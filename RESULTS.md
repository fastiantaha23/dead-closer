# Benchmark results

Generated by `python -m bench.simulate`, `python -m bench.safety_suite` and `scripts/render_results.py`. Backend: **rules** (offline rules engine, deterministic; no LLM calls).

## 1. Speed (measured)

First-reply latency, 300 sequential new leads on an idle machine (sqlite file + sqlite checkpointer, idle machine); this is the whole engine: LangGraph, checkpointer, SQLite, NLU, safety guards, rendering:

| p50 | p95 | p99 | worst | within 60 s SLA |
|---|---|---|---|---|
| 15 ms | 45 ms | 78 ms | 119 ms | 100.0% |

Inside the 12 simulation runs (6 processes sharing one laptop CPU, so inflated by contention) the first reply was p50 33 ms, p95 97 ms, p99 197 ms, worst 484 ms, 100.0% within 60 s.

Burst load test: **300 simultaneous new leads** (+ a reply each) on sqlite file + sqlite checkpointer with 32 workers: sustained 19.3 new-lead conversations/s (one instance, 32 client threads, single short burst - do not extrapolate to hourly volume without a soak test), first reply p50 877 ms, p95 1292 ms, p99 1415 ms, max 1568 ms, 100.0% within the SLA.

All 300 leads of the burst were answered inside the SLA; the queue is serialized by SQLite + the GIL, so the burst p95 is the time to drain the queue. With the Claude backend enabled add model latency per call (understand + compose, so two calls per message; not measured here). Run `DEADCLOSER_LLM=claude python -m bench.simulate --perf` to measure it with your key.

## 3. Conversion and revenue (simulated leads - read the caveat)

400 leads per run, seeds [1, 2, 3], 35 virtual days, real scheduler. Mean ± std over seeds.

| Variant | Booking rate | Revenue / 100 leads | Billable share of bookings | Bookings after a follow-up | Low-intent leads billed / booked |
|---|---|---|---|---|---|
| Full agent | 30.6% ±2.4 | $1025 | 73% | 36% | 3.3 / 8.3 |
| No follow-ups | 19.5% ±0.6 | $668 | 76% | 0% | 2.0 / 5.3 |
| No qualification questions | 33.5% ±2.1 | $423 | 28% | 35% | 1.7 / 12.3 |
| Human-speed first reply (4 h) | 12.8% ±0.8 | $448 | 77% | 35% | 3.0 / 4.7 |

**What to take from it:** follow-ups and fast replies add bookings; removing qualification adds *unqualified* visits but they are not billable, so revenue falls (the billing guard removes any incentive to pad visits).

"Low-intent" counts the browser, price-sensitive, disinterested and adversarial personas. Browsers who book are never billed (0 of 5 in seed 1, see below); the billed ones are almost all price-sensitive leads whose stated budget fits a cheaper listing, which the billing rule treats as qualified - arguably genuine buyers, so read that column as an upper bound on false billing.

**Caveat:** lead behaviour (reply/booking probabilities per persona, and that a 4-hour reply loses 60% of leads) is *assumed*, so absolute booking rates are illustrative. Assumptions are in `bench/simulate.py` (`PERSONAS`, `SLOW_PENALTY`) and `simulation.json`. The comparison between variants uses identical simulated leads and is the useful signal. Real performance must be measured in a pilot.

**Honest notes on the safety score.** The suite was written alongside the agent. Its first run scored 92/100 and found real bugs (PII was redacted *before* it was detected so it was never audited; two escalation phrasings were missed; a password-request produced a false PII warning) - all fixed, and tests added. A later end-to-end test caught a default business address leaking another tenant's name (the output guard blocked it; the default was removed). Because decisions are code and the LLM only words a plan, prompt-injection resistance here is structural; with the Claude backend the same suite should be re-run (`DEADCLOSER_LLM=claude python -m bench.safety_suite`) - that run has **not** been performed for this report. Passing 100% of your own tests is not a guarantee against unseen attacks; treat it as a regression gate.
